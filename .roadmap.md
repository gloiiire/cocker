# Cocker Roadmap

## Positioning

> **Cocker = Docker-compatible container engine for Apple Silicon, optimized for projects in iCloud Drive.**

We don't compete with `apple/container` on its own terms (native XPC, sophisticated
init, `container machine`). Apple's resources >> ours ; trying to match them
feature-for-feature wastes effort and dilutes identity.

What we own that they don't :

- **Docker Engine API v1.41** on a Unix socket → `DOCKER_HOST=unix://~/.cocker/docker.sock`
  makes `docker compose`, VS Code Dev Containers, IDE plugins, CI runners,
  `docker buildx`-style tooling all work without modification.
- **iCloud Drive awareness** — staging, materialization, FSEvents-based hot
  reload. Apple ignores this case ; lima/colima don't address it either.
- **Block-storage volumes (ext4 .img)** — postgres / mysql / redis crash on
  virtiofs (chown EPERM, lost+found, FUSE inode inconsistency). We mount real
  block devices via VZVirtioBlockDevice ; they Just Work.

## Rules of engagement

For every new feature, ask :

> *Does this bring cocker closer to Docker, or further from it ?*

- **Closer** (e.g. `compose watch`, `.dockerignore`, anonymous volume seeding,
  `compose logs -f`) → ship it.
- **Further** (e.g. a persistent VM mode, a Swift agent inside the container, a
  TOML config language) → punt. Redirect the user to `apple/container` or
  another tool that already does it.

Width kills solo projects. Focus keeps them alive.

## Mid term — this month — Close the real Docker gaps

### Must-have

- `cocker compose exec -it <svc>` — confirm interactive TTY allocation works end to end.
- `cocker stats` — live resource usage. Currently a stub ?
- `cocker context` — multi-daemon support. Audit completeness.
- Healthcheck `start_period` honored when set via compose (verify wiring).

### Worth auditing

- `cocker login` against ECR / GHCR / GAR — corporate workflows.
- `cocker push` to a private registry — easy to overlook in forks.
- Custom network drivers (Tailscale, mesh networks) — bonus differentiator.

### To PUNT (remove from `-h`, redirect in docs)

- `swarm` / `stack` / `service` / `node` — cluster orchestration nobody runs on
  a single Mac.
- `buildx` multi-platform — unless someone explicitly asks. Most Mac devs only
  need arm64.
- MCP stubs — only if there's active demand. Otherwise they bloat `-h`.

Showing fewer commands in `-h` IS focus. The help text should advertise what
cocker does **well**, not everything it has ever tried.

## Long term — this quarter — Deepen the moat

### iCloud-aware compose, at maximum

- **Incremental rebuilds on watch** — only the services whose source files
  actually changed, not the whole project. Build cache awareness per service.
- **Dataless detection mid-build** — if a file is still `notDownloaded` when a
  `COPY` reaches it, fire `startDownloadingUbiquitousItem` and wait inline
  rather than failing.
- **Cross-run cache invalidation** — touching an iCloud file should invalidate
  the matching layer in the next build, even if the rsync stage already finished.

### IDE-first workflow

- Document `DOCKER_HOST=unix://~/.cocker/docker.sock code .` for VS Code Dev
  Containers.
- Document the equivalent for JetBrains' Docker integration.
- Investigate a Zed terminal plugin / inline pickers reading our completion
  scripts.

### Performance on Mac

- Measure cold-start time of a `cocker run alpine echo hi`. Target sub-1s
  (`apple/container` is ~2s).
- Investigate a warm VM pool : pre-booted alpine VMs ready to exec a container
  in milliseconds.
- Profile virtiofs throughput vs block-storage for typical workloads.

### Relationship with `apple/container`

- Document the clean split : use `container machine` for persistent dev VMs,
  use `cocker` for Docker-compatible container workflows. No overlap, no
  competition.
- Watch for upstream changes that affect us (kernel ABI, initrd format,
  containerization library bumps).
- Contribute upstream when we hit bugs in their kernel / initrd — it builds
  credibility and reduces our maintenance burden.

## Anti-roadmap — explicitly NOT doing

- A persistent VM mode à la `container machine` / Lima / colima. Wrong audience.
- A Swift-based init agent inside the guest. Our C / musl init is the right
  size for the Docker model.
- A custom configuration language. Env vars + flags + compose files cover
  every realistic config need.
- Out-of-tree network drivers as a public plugin API. Internal abstraction
  yes, public ABI no — too much surface to maintain.
